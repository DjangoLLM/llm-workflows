Pi Agent × MCP Bridge

How a TypeScript LLM worker uses Python-registered tools — without touching MCP itself.

Temporal
Workflow starts
Python PiMcpLoopWorkflow orchestrates the whole turn. Knows the toolset name; kicks off activities.
MCP · Python
List tools
Activity spawns run_tools_mcp --toolset echo as an STDIO subprocess. FastMCP client calls list_tools() and translates to plain JSON schemas.
TypeScript
piInference
Tool schemas arrive as PiInferenceTool[]. LLM sees them as native tools. If it picks one it returns toolCalls. Zero MCP knowledge here.
MCP · Python
Call tool
Activity spawns a new STDIO subprocess, calls call_tool(name, args), returns the structured output as JSON.
Temporal
Loop / return
Workflow stitches the tool result into the next user message and re-calls piInference until no more toolCalls.

1 · What the pi-worker expects

TypeScript · unchanged
The pi-worker is not modified. It already had a tools? slot in its input and a toolCalls slot in its output. We just fill the former and read the latter.

2 · The bridge

MCP · Python
PiMcpBridge is an async context manager that holds one STDIO subprocess open. It exposes two operations: list the tools (MCP → pi-worker JSON) and call a tool (pi-worker JSON → MCP → result).
tools/mcp/pi_bridge.py data shapes 
@dataclass(slots=True, frozen=True)
class PiInferenceTool:
    # Mirrors the TypeScript PiInferenceTool exactly.
    name:        str
    description: str
    parameters:  dict[str, Any]       # JSON Schema from MCP inputSchema

    def to_dict(self) -> dict:
        return {"name": self.name, "description": self.description,
                "parameters": self.parameters}


@dataclass(slots=True, frozen=True)
class PiToolResult:
    name:          str
    arguments:     dict[str, Any]
    output:        Any                 # whatever the tool returned
    is_error:      bool
    error_message: str | None = None
tools/mcp/pi_bridge.py PiMcpBridge — long-lived subprocess + client 
class PiMcpBridge:
    """Holds one MCP STDIO subprocess open for multiple ops."""

    @classmethod
    def for_toolset(cls, toolset_name, *, cwd=None, ...) -> "PiMcpBridge":
        command = [python, "manage.py", "run_tools_mcp",
                   "--toolset", toolset_name, "--transport", "stdio"]
        return cls(command, cwd=cwd, ...)

    async def __aenter__(self):
        transport = StdioTransport(command=..., args=..., env=..., cwd=...)
        self._client = await Client(transport).__aenter__()
        return self

    async def list_tools(self) -> list[PiInferenceTool]:
        raw = await self._client.list_tools()
        return [
            PiInferenceTool(
                name=t.name,
                description=t.description or "",
                parameters=t.inputSchema,  # already JSON Schema
            )
            for t in raw
        ]

    async def call_tool(self, name, arguments) -> PiToolResult:
        try:
            result = await self._client.call_tool(name, arguments)
            return PiToolResult(name=name, arguments=arguments,
                                  output=result.data, is_error=False)
        except ToolError as exc:
            return PiToolResult(name=name, arguments=arguments,
                                  output=None, is_error=True,
                                  error_message=str(exc))

3 · Temporal activities

Python · agents worker
Thin wrappers that expose the bridge as Temporal activities. The workflow calls these by name; the agents worker executes them locally, spawning the MCP subprocess each time.
temporal/mcp_pi_activities.py 
@activity.defn(name="agents.mcp.list_pi_tools")
async def list_pi_tools_activity(
    toolset_name: str,
    cwd: str | None = None,
    python_bin: str | None = None,
    manage_py: str = "manage.py",
) -> list[dict]:
    tools = await discover_pi_tools(
        toolset_name, cwd=cwd, ...)
    return [t.to_dict() for t in tools]

    tool_name: str,

    cwd: str | None = None,

        toolset_name, tool_name, arguments, ...)

4 · The workflow loop

Python · Temporal workflow
The workflow is the glue. It calls three different activities — two Python (MCP), one TypeScript (LLM) — stitching the outputs together into a conversation until the model has no more tool calls to make.
examples/feedback_demo/feedback/pi_mcp_workflow.py PiMcpLoopWorkflow.run() 
@workflow.run
async def run(self, input: PiMcpLoopInput) -> PiMcpLoopOutput:

    # ① Discover tools — spawns STDIO MCP server, gets JSON schemas
    tools = await workflow.execute_activity(
        "agents.mcp.list_pi_tools",               # Python activity
        args=[input.toolset_name, input.mcp_cwd, ...],
        start_to_close_timeout=timeout,
    )

    messages = [{"role": "user", "content": input.user_message}]

    for iteration in range(1, input.max_iterations + 1):

        # ② Call the LLM — routes to TypeScript pi-worker
        pi_output = await workflow.execute_activity(
            pi_inference_stub,                        # TypeScript activity
            {"messages": messages, "tools": tools, ...},
            task_queue="pi-inference-queue",          # ← routes to TS worker
            start_to_close_timeout=timeout,
        )

        calls = pi_output.get("toolCalls", [])
        if not calls:
            return PiMcpLoopOutput(
                final_text=pi_output["finalText"],
                iterations=iteration, ...)

        # ③ Dispatch each tool call through MCP
        for call in calls:
            result = await workflow.execute_activity(
                "agents.mcp.call_pi_tool",            # Python activity
                args=[input.toolset_name,
                      call["name"], call["arguments"], ...],
                start_to_close_timeout=timeout,
            )
            # ④ Fold result back as next user message → loop
            messages.append({
                "role": "user",
                "content": f"<tool_result>{json.dumps(result)}</tool_result>",
            })

5 · Protocols at each hop

Hop Protocol Between
Workflow → list_pi_tools activity Temporal gRPC Python ↔ Python
list_pi_tools activity → MCP server MCP over STDIO Python ↔ Python subprocess
Workflow → piInference Temporal gRPC (cross-queue) Python workflow → TypeScript worker
piInference → LLM provider HTTPS / OpenAI API TypeScript ↔ external
Workflow → call_pi_tool activity MCP over STDIO Python ↔ Python subprocess
The TypeScript pi-worker only ever sees Temporal RPC. MCP stays inside the Python process and never crosses the polyglot boundary.
