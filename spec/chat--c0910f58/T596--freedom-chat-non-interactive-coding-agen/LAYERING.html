Why isolate it

It's already standalone — only its filing was wrong.

zero couplingpure stdlib + subprocess — no Django, pydantic_ai, or agents imports
no inbound usenothing in production imports it today; only tests do
wrong neighboursits beside core/agent.py — a pydantic_ai LLM, a different concern
one jobdrive external coding CLIs over a pipe, non-interactively

Dependency graph

04

Inside the package

Break the 1209-line monolith into one-job modules; __init__ re-exports the public surface.

policy.pyNonInteractivePolicy, CODING_AGENT_POLICY, OutputFormat
events.pyCLIEvent, CLIResponse, event aggregator
base.pyBaseCLIWrapper — subprocess, stream, timeout/kill
claude.pyClaudeCLIWrapper (already written)
codex.pyCodexCLIWrapper
gemini.pyGeminiCLIWrapper
pi.pyPiCLIWrapper
resilient.pyResilientCLIWrapper — retry wrapper
registry.pyget_coding_agent(name) → factory
__init__.pypublic re-exports (the only import surface)
05

The seam

Consumers talk to an interface + a factory — never to wrapper classes. That's what makes it a layer, not a moved file.

# coding_agents — public surface def get_coding_agent(name: str, *, working_dir, model=None) -> CodingAgent: ... class CodingAgent(Protocol): def stream(self, prompt, policy) -> AsyncIterator[CLIEvent]: ... async def run(self, prompt, policy) -> CLIResponse: ... # freedom-chat — the only thing chat ever sees agent = get_coding_agent("claude", working_dir=repo) async for ev in agent.stream(prompt, CODING_AGENT_POLICY): push_to_chat(ev) # CLIEvent → chat message
✓
Net effect
Codex / Gemini / Claude become swappable behind one factory; the non-interactive policy is the contract crossing the boundary; freedom-agents sheds a concern it never used in production. The actual T596 work is this layer + its CLIEvent → chat seam — the Claude wrapper itself already exists.
