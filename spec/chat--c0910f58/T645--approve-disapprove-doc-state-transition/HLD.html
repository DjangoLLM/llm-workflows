Approve/Disapprove Design Docs to Advance Linked Stories

A human approval gate lives in the app shell around existing design-doc tabs. Approve can move the linked story across a configured Plane state edge; Disapprove records a durable decision without changing Plane. The generated HTML document never renders those action controls.
Phase: HLD Manual path coexists with agent self-advance Guarded live-state transition Doc HTML stores metadata only
Problem Decisions System Shape Approve Flow Trace Files Acceptance

Problem

The same design document can be relevant to different Plane workflow edges over a story's life, and the doc agent may already have advanced the story before a reviewer clicks Approve.

Today

The app renders generated HTML in a sandboxed iframe while agents can update Plane state themselves from workflow prompts.

->
Risk

A stale click must not move a story to the wrong next state when live state has changed.

->
Target

Approve resolves an edge, guards live state, then transitions by state ID. Disapprove records the decision only.

Design Decisions

The HLD keeps authority on the server side for state resolution, guarding, and persistence, while the app viewer owns the action chrome around the sandboxed document.

Edge source

Document stamp only

A generated document may stamp a current/next pair as metadata, never as action UI. If absent, the server uses the selected profile's state-edge map keyed by the story's live current state.

Transition guard

Live state is authoritative

The server re-fetches the story immediately before transition. If it is no longer in the expected current state, the request returns a clear no-op.

Disapproval

Record, do not move

Disapprove writes a decision row with doc, task, state-at-decision, timestamp, and optional note. Plane state is unchanged.

Approve Flow

Approval is a guarded server transaction. A stale click is a successful no-op, not an accidental transition.

Step Mechanic Failure behavior
1 Frontend posts `doc_id`, selected task, selected project, and profile index. Missing context returns an explicit error.
2 Backend loads the registry row and validates the document belongs to the selected task. Mismatch is rejected; no path parsing fallback.
3 Backend parses the document's metadata-only state-pair stamp or falls back to the profile map. Malformed override or missing map entry returns a clear error/no-edge result.
4 Backend re-fetches live task details and compares current state to expected current. Different state returns no-op conflict: "story is in X, expected Y".
5 Backend resolves current and next names against live project states, then updates by next state ID. Unknown state names and update failures surface loudly to the UI.

Acceptance Signals

Ready for LLD when: the design preserves agent self-advance, adds an app-owned manual approval path with live-state guarding, keeps approve/disapprove controls out of generated HTML, resolves states by name against live Plane state IDs, returns explicit conflict/error messages, and records Disapprove decisions with a nullable note for future rework automation.
